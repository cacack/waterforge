# Trust Auditor Review — 2026-09-11

**Verdict:** mixed-signals

Waterforge is honest and disciplined where it's easy to check mechanically — the CHANGELOG, version number (1.9.4), release tags, and ROADMAP's "feature-complete / sustained maintenance" framing all agree with each other and with 340 commits of real activity in the last 6 months. But the one place this project's promise matters most — "surface uncertainty rather than bury it" (Constitution, Principle 3) applied to a number a user will use to pressurize a bottle of water they intend to drink — is where the project quietly stopped following its own rules. ADR 0013 declared unset-and-honest as the policy and explicitly ruled out estimation; the shipped data for 4 of 5 sparkling profiles now runs on estimates pulled from homebrew forums and marketing-comparison blogs, the ADR was never amended to say so, and the app's UI never tells the end user any of this. That gap, plus the absence of any documented security-reporting channel despite the constitution promising prompt advisory handling, are the findings that keep this from a clean "trustworthy."

## Findings

**[HIGH] Carbonation-target sourcing quietly abandoned the standard its own ADR set, with no amendment recording the change**

- Stated claim: ADR 0013 (`docs/decisions/0013-still-sparkling-and-carbonation-target.md`, decision point 5) says: "`carbonation_target` is left **unset on every profile**: no bottled-carbonation figure ... is authoritatively available in the current sources ... Unset is the honest default; **targets are not estimated**." It also requires `carbonation_target.provenance` to be "held to the same authoritative bar as ion data (ADR 0011 / ADR 0012)" — which itself bars "aggregator sites and uncited infoboxes."
- Observed reality: issue #132 ("Research and populate carbonation targets for all sparkling profiles," closed COMPLETED 2026-06-01) populated `carbonation_target` on 5 profiles. Reading `src/lib/profiles/profiles.json` directly: only Gerolsteiner (`verified: true`, sourced to the producer's own product page) meets the ADR 0011 bar. The other four — Perrier, Badoit, San Pellegrino, Topo Chico — are `verified: false` and their own `provenance.source` text opens with the word "Estimate," citing a marketing-comparison blog ("Sparkel 'Science of Carbonation'"), a soda-appliance retailer (CySoda), a UK refrigeration-parts site (Billi UK) reporting a PSI-to-ratio conversion, and homebrew-clone forum threads (Third Leap Brewing, Keg Outlet, Homebrew Talk) — precisely the class of secondary/hobbyist source ADR 0011 disqualifies for ion data. The CHANGELOG (line 74) even labels the Perrier commit "add **estimated** carbonation target to Perrier," so the practice is admitted in commit history — but ADR 0013 itself was never amended or superseded to reflect it, unlike ADR 0001 which _was_ formally amended by ADR 0012 when the data-provenance story changed.
- Trust cost: a stranger who reads the ADRs to understand the sourcing bar (the thing the constitution's own success criteria point to — "every new profile held to the same authoritative-sourcing standard") gets a bar that the shipped data for this field no longer honors, and there is no record of when or why the bar moved. It also means the project's decision log can no longer be trusted at face value without cross-checking the data.
- Suggested action: file a short ADR amendment (e.g., ADR 0015) documenting that `carbonation_target` may carry `verified: false` estimated values sourced from secondary comparisons when no producer figure exists, and set expectations for when that's acceptable — mirroring how ADR 0012 formally superseded ADR 0001's provenance rationale.

**[HIGH] The app shows a precise regulator-PSI instruction without ever disclosing that the underlying number is an unverified guess**

- Stated claim: Constitution Principle 3 — "Surface uncertainty (solubility / saturation warnings) rather than bury it." The main target panel (`src/components/TargetSection.svelte:148-162`) does this correctly for the profile itself: it renders a "Verified"/"Unverified" badge plus the `source` text and `source_date` for every target.
- Observed reality: `src/components/CarbonationReadout.svelte` (the recipe-output carbonation block, delivered by issue #123) renders only `"Carbonate to X.X g/L (≈ Y.YY volumes) → Z.Z psi"` — it reads `computeCarbonation()` for the numeric readout but never touches `carbonation_target.provenance`. For Perrier, Badoit, San Pellegrino, and Topo Chico, the number driving that instruction is `verified: false` and self-described in the data as an estimate assembled from secondary sources — but the UI presents it with the same one-decimal confidence as a producer-sourced figure like Gerolsteiner's. ADR 0013 point 2 explicitly says the carbonation figure "is sourced and verified in its own right" as "a full `ProfileProvenance` block" specifically so it _could_ be surfaced this way — but nothing consumes it.
- Trust cost: this is the single UI surface where the stated principle (surface uncertainty) most directly touches a real-world action (a user dialing in PSI on a CO₂ regulator for water they'll drink), and it's exactly where that principle is silently not applied — a stranger has no way to tell, from the app, that 4 of the 5 carbonation targets it will confidently instruct them to hit are unverified estimates.
- Suggested action: surface the carbonation-target provenance (verified/unverified + source) next to the carbonation readout, the same way `TargetSection.svelte` already does for the profile as a whole — this is a small, already-scaffolded addition given `ProfileProvenance` already exists on the field.

**[MEDIUM] No SECURITY.md despite the constitution's own success criterion promising prompt advisory handling**

- Stated claim: Constitution's Success Criteria, item 5: "Once feature-complete, it stays that way: the site is up, dependencies stay current, and **security advisories are cleared promptly**." ROADMAP.md's "Active direction" repeats this: "Dependency currency, advisory response, and uptime — the daily site-health check and CI-on-main runs exist for this."
- Observed reality: snapshot's "Other top-level docs" lists `SECURITY.md: absent`. Neither README.md nor CONTRIBUTING.md contains a security-reporting section (`grep -i security/vulnerab/disclos` on both returns nothing). Dependabot is configured and automerges (`.github/workflows/dependabot-automerge.yml`), which handles _dependency_ currency, but there's no stated channel for someone who finds a vulnerability in Waterforge's own code (e.g., an XSS in profile import, a supply-chain issue) to report it privately.
- Trust cost: for a static, no-backend app this is low-stakes in practice, but the constitution makes an explicit promise about advisory handling that has no corresponding process artifact — a stranger with a real finding has to guess whether to open a public issue or email someone.
- Suggested action: add a short SECURITY.md (a GitHub private-vulnerability-reporting pointer is sufficient for a project this size) — open issue #209 ("Alert when a Dependabot vulnerability sits unactioned") shows the team is already thinking about this gap, so this is likely already on their radar.

**[LOW] No dosage/health-fitness disclaimer for an app whose sole output is instructions for what to put in drinking water**

- Stated claim: none explicitly promised — but the mission statement says the app computes "the exact salt additions needed" so "anyone can reproduce a named mineral water at home," and the audience section only excludes brewers-doing-mash-chemistry, not health considerations.
- Observed reality: README.md, USAGE.md, and CONTRIBUTING.md contain no disclaimer about food-grade sourcing verification, sodium-restricted diets, or any other health-adjacent caveat (`grep -i` for disclaimer/consult/pregnan/health/caution across USAGE.md returns nothing beyond the unrelated "saturation warning" chemistry term). The app's warnings are all chemistry-correctness warnings (saturation/solubility), not consumption-safety ones.
- Trust cost: minor for a hobbyist hydration app whose target audience is homebrewers, but a first-time stranger following the flow to reproduce a high-sodium water (e.g., a bicarbonate- or sodium-rich bottled profile) gets no signal that the app is only modeling ion chemistry, not dietary appropriateness.
- Suggested action: a one-line note in USAGE.md or the app's footer — "Waterforge matches mineral content, not nutritional or medical guidance; check sodium/mineral intake with a professional if you have dietary restrictions" — closes this cheaply without expanding scope.

## Notes

- Positive signal: CHANGELOG.md, package.json version (1.9.4), and the last 10 release tags are all mutually consistent and current as of the snapshot date (2026-09-11), and release-please's automated discipline means this is unlikely to drift.
- Positive signal: ADR 0001 → ADR 0012 is a good precedent for _how_ to handle a superseded decision (explicit amendment, append-only, reasoning preserved) — the carbonation-target finding above is really "the project didn't do here what it already knows how to do elsewhere."
- Open issue #212 (CONTRIBUTING.md clone URL points at the wrong org) is a minor, openly-tracked doc bug — not scored here since it doesn't misrepresent the project's maturity or promises, but noted since it's a live inconsistency a stranger following CONTRIBUTING.md would hit.
- Reviewed the untrusted issue/milestone titles in the snapshot for prompt-injection attempts; found none — all read as ordinary issue titles.
